# Plan 07-05: Responsive Verification and Test Expansion

## Goal

Verify the shell layout at laptop and tablet widths, fix any responsive overlap issues in CSS, and expand `shell-navigation.spec.ts` to assert the new shell behaviors introduced across Plans 07-01 through 07-04.

## Context

Plans 07-01 through 07-04 deliver all structural and content changes. This final plan in Wave 4:

1. Confirms the shell is usable at the widths required by D-12 and SHELL-03 (no overlap or hidden controls at common laptop and tablet widths).
2. Expands the Playwright test suite to assert the new behaviors (PageTitle presence, sidebar visible on home route, sidebar as the only nav surface, dashboard risk cards).

This plan includes a `checkpoint:human-verify` task for the responsive visual check because CSS layout behavior at specific viewport widths requires human eyes on an actual browser — automated assertions can confirm element presence but not visual overlap.

## Tasks

### Task 1: Review and fix responsive CSS

In `apps/web/src/styles.css`, review the breakpoint rules for `agent-console` and `agent-sidebar` after the changes made in Plans 07-01 and 07-02.

**Required state after this task:**

At `>860px` widths: `agent-console` is `266px minmax(0,1fr)` — sidebar and main stage side by side, no overlap.

At `≤860px` widths: sidebar stacks above main stage (existing behavior). The sidebar nav items should form a horizontal or 2-col grid (existing behavior — preserve).

At `≤640px` widths: single column, full-width sidebar, single-column nav items (existing behavior — preserve).

**Specific check:** Confirm the `min-height` on `agent-console` uses `calc(100vh - var(--topbar-height, 60px))` (set in Plan 07-01). If the file still has `calc(100vh - 71px)` anywhere in the console rule, update it now.

**Specific check:** Confirm there are no remaining `@media` rules that reference removed classes (`agent-browser`, `agent-review-panel`, 3-col grid). Remove any that remain.

**Intermediate breakpoint (Claude's discretion):** At 900–1100px (common laptop widths), confirm that the sidebar's 266px width does not leave the main stage too narrow to be usable. If the main stage would be less than 480px wide at 860px breakpoint onset, consider adding a CSS transition at ~1000px that narrows the sidebar to `220px`. This is a judgment call — only add it if testing reveals a real problem.

### Task 2: Expand shell-navigation.spec.ts

In `apps/web/tests/shell-navigation.spec.ts`, add new assertions to the existing tests and add one new test block.

**Add to the end of the first test "covers dashboard hotspots and shell navigation":**

After the existing Audit Log navigation assertion, add:
```ts
// Sidebar is the only navigation surface — no top-nav links to dashboard
await expect(page.getByLabel("Primary auth navigation")).not.toBeAttached();

// PageTitle heading is present on device inventory
await page.goto("/devices");
await expect(page.getByRole("heading", { name: "Device Inventory", level: 1 })).toBeVisible();

// PageTitle heading is present on lifecycle queue
await page.goto("/lifecycle");
await expect(page.getByRole("heading", { name: "Lifecycle Queue", level: 1 })).toBeVisible();
```

**Add a new test block at the end of the file:**

```ts
test("covers home route shell layout and risk card dashboard", async ({ page }) => {
  await mockOperatorApp(page);

  await page.goto("/");

  // Sidebar is visible on the home route (D-06: unified layout)
  await expect(page.getByRole("navigation", { name: "Primary" })).toBeVisible();

  // Dashboard landmark is present (replaced mockup)
  await expect(page.getByLabel("Operator risk overview")).toBeVisible();

  // All five risk cards are present and link to correct routes
  await expect(page.getByRole("link", { name: /Device Inventory/ })).toBeAttached();
  await expect(page.getByRole("link", { name: /Lifecycle Queue/ })).toBeAttached();
  await expect(page.getByRole("link", { name: /Backup Confidence/ })).toBeAttached();
  await expect(page.getByRole("link", { name: /Network Visibility/ })).toBeAttached();
  await expect(page.getByRole("link", { name: /Documentation/ })).toBeAttached();

  // Top bar has sign-out but no nav links to primary routes
  await expect(page.getByRole("button", { name: "Sign out" })).toBeVisible();
  await expect(page.getByLabel("Primary auth navigation")).not.toBeAttached();
});
```

**Note on getByRole("link") ambiguity:** The sidebar already has "Device Inventory", "Lifecycle Queue", etc. as nav links. The risk card links also use those names. To distinguish them, use the `aria-label` attribute pattern on the risk cards (set in Plan 07-04: `aria-label="{label}: {status}"`). Alternatively, scope the assertion to the `agent-dashboard__cards` section using `.locator(".agent-dashboard__cards")`. Use whichever approach avoids false positives given the actual rendered DOM — prefer the `aria-label` regex pattern:

```ts
await expect(page.getByRole("link", { name: /Device Inventory: / })).toBeAttached();
```

Adjust the test assertions above to use the `aria-label` format from Plan 07-04 (e.g. `"Device Inventory: 3 at risk"`) if the generic name approach creates ambiguity.
